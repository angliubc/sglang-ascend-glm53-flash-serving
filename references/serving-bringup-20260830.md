## Bug catalog (8 fixes, each = one ~4min deploy cycle)

1. **NoPE rope views in ascend_backend** (closed the long-open item): `k_rope.view(-1, H, qk_rope_head_dim)` and friends crash with 0-dim (`[-1,…,0]` ambiguous reshape on 0-element tensor). Probe (`probe_nope_fia.py`, privileged container, `import custom_ops`): **`npu_fused_infer_attention_score` accepts MLA calls with rope kwargs entirely omitted** (mathematically exact for NoPE: score = q_nope·c_kv) but rejects rope tensors of dim 0 or 1 (kernel error 561002). Fix pattern (14 sites in `ascend_backend.py`): guard every rope view with `if self.qk_rope_head_dim > 0`, else `None`; pass FIA rope kwargs conditionally: `**(dict(query_rope=q_rope, key_rope=k_rope_cache) if self.qk_rope_head_dim > 0 else {})` (4 sites at 16-space indent + k_pe variants at 12/16/20-space in forward_sparse CP/target-verify/second-decode paths — variable names differ per site: `q_rope`/`q_pe`/`q_rope_prev`/`q_rope_next`).
   **Trap**: the NPU MLA KV pool stores ONE packed buffer `[size, 1, kv_lora_rank + qk_rope_head_dim]` and `get_kv_buffer` returns it for BOTH key and value. The variable named `k_rope` in ascend_backend is that packed buffer — never a real rope tensor. On NoPE the rope cache must be `None` (reshape-0 of the 114M-element packed buffer is wrong twice over).

2. **`--disable-radix-cache`**: `MambaComponent requires page_size=1 when mamba_extra_buffer is disabled, got 64`. Hybrid (KDA) models hit this at scheduler init. Production GLM-5.2 on the same cluster runs with `--disable-radix-cache` (verified via `ps aux | grep launch_server` on node1) — mirror it.

3. **transformers patchify >8 dims**: glm5_next image processor does `unsqueeze(6).expand(-1,…,T,-1,-1)` = 9-D → NPU copy ops cap at 8 dims ("The self tensor cannot be larger than 8 dimensions", copy_d2d inside tokenizer-manager during multimodal warmup). Fix: pre-merge the last two P dims to 7-D, unsqueeze T, 8-D expand — element order preserved exactly (a size-1 or inner merge of contiguous dims never changes flat order; T must stay BETWEEN C and P in the flatten order). Delivered as a bind-mount over site-packages (`-v /data/models/patch/image_processing_glm5_next.py:.../transformers/models/glm5_next/image_processing_glm5_next.py:ro`), since the overlay only covers sglang.

4. **Vision tower inductor crash**: torch_npu's `_inductor/codegen/ir.py detect_flattened_axis` → `KeyError: s94 + 1` when the multimodal warmup image hits the vision encoder (something inside compiles). For text-serving bring-up: `--skip-server-warmup` + a manual TEXT `/v1/completions` curl. (`--language-only` is NOT the tool — it means VLM encoder-disaggregation and rejects glm5_next.)

5. **KDA gate 3-D/4-D**: `fused_kda_gate_npu` got `heads*head_dim != hidden` because daily's `_prepare_extend_gate_inputs` does `g.flatten(-2)` assuming g is 4-D `[B,T,H,D]`, but glm5_next passes 3-D `[B,T,H*D]` → flatten merges T into hidden (512→3072). Fix: `(g if g.dim() == 3 else g.flatten(-2))` (kernel reshapes internally). One-line debug print of `g.shape / A_log.shape / head_k_dim` settles it in one cycle.

6. **CANN 207001 misdiagnosis** (the big one): `aclnnBatchMatMul error 207001 "Binary get function by entry Failed"` on node4 ranks during prefill, mhc `_mhc_pre_torch` F.linear. Looks like "kernel binary missing for this shape". Standalone probes of the exact shapes (fp32 AND bf16, m=1..8192) PASS on both nodes' NPU containers. Real cause: **long-prefill memory blowup** — `x_flat [T,16384]` fp32 + `.square()` + mean ≈ 3-4GB at 16k tokens vs ~1.3GB free after graph capture → tiling/buffer allocation inside the op fails and CANN misreports it. Fix: chunk `_mhc_pre_torch` at 1024 tokens (bf16 GEMM, fp32 accumulation only on `[chunk, 24]` mixes; sinkhorn tiny). The diagnostic tell: **same op+shape passes in an idle-NPU probe container but fails in-serving → suspect memory, not the binary.**

7. **mHC fused kernels genuinely unavailable**: `npu_hc_pre_sinkhorn` has a torchair converter `.py` with a glm5_next-1:1 signature (`mixes, rsqrt, hc_scale, hc_base, x, hc_mult, iters, eps → (y, post, comb)`) but `aclnnHcPreSinkhorn` (and `aclnnHcPre`) are NOT in libopapi.so of either the v0.5.16 quant base or the daily-cann9.0.0 image. Converter .py ≠ shipped binary. Torch fallback (chunked, see #6) is the only path.

## Diagnosis workflow that worked

- **Hanging request, no exception**: py-spy the scheduler (`scheduler_TP0`) — the stack names the exact op/file/line. If it shows a compile/enqueue line, it's JIT or a stream wait, not a deadlock.
- **Hanging request on a 2-node TP deployment**: CHECK THE PEER NODE'S CONTAINER FIRST. TP collectives block silently when any rank dies; the surviving side's py-spy shows an innocent enqueue line (e.g. an elementwise sum) while the dead peer has the real traceback. Symptom pattern seen: node3 "hangs", node4 crashed with the actual error.
- **Instrument one line, one cycle**: drop a shape-print env-gated (`DEBUG_NOPE`) right at the failing call, relaunch, one request, read shapes — cheaper than source archaeology when signatures are ambiguous. (Insert OUTSIDE ternary expressions; a print inside a ternary's else-branch is a syntax error — one botched instrument cost a restore-from-peer cycle. Restore base files from the UNTOUCHED peer node when you corrupt one: the overlay tree is rsync-replaceable, but image-base files (ascend_kda_backend.py) aren't in the port tree.)
- **Probe containers**: `docker run -d --name hcprobe --privileged --security-opt label=disable --device /dev/davinci0 … -v /data/models/scripts:/probe <image> sleep 300` — same flag set as production (a minimal --device probe indicts the flags, not the code). `import custom_ops` REQUIRED to register `torch.ops.custom.*` (importing sglang wrappers does not).
